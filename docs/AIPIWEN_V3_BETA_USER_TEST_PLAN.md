# AIPIWEN V3.0 Beta 用户测试计划

生成时间：2026-07-24 23:58 PDT

## 1. 测试目标

用 5-10 名受控测试用户验证 AIPIWEN 指导师工作台 V3.0 的真实账号闭环，重点观察：

- 用户能否独立完成登录、注册和进入工作台；
- 普通指导师、机构身份和既有账号的权限是否符合规则；
- 钱包、积分流水和邀请码是否来自真实业务数据；
- 邀请关系是否在完整注册流程中保留；
- 手机端是否存在输入、跳转、导航或信息理解障碍。

本轮不测试支付、充值、微信登录、真实 AI 模型或真实客户系统。

## 2. Beta 入口

本批测试固定使用以下 Preview 部署，不使用 `aipiwen.cn` 首页入口：

`https://aipiwen-ai-understanding-99r5kuzk9-guo-yanling-s-projects.vercel.app/login.html`

Release Commit：

`4e2c0e4dbffa94cc4b809f49559b317d9cb0bb30`

测试人员不得转发公开渠道。每位测试人员使用独立测试手机号，不在截图、反馈或群聊中展示完整手机号、短信验证码、密码、Cookie 或 Session 信息。

## 3. 建议测试用户组成

| 类型 | 建议人数 | 说明 |
| --- | ---: | --- |
| 用户 A：普通指导师 | 3-4 人 | 覆盖首次注册和自动开通 |
| 用户 B：机构身份 | 1-2 人 | 至少各覆盖一次服务中心或分公司 |
| 用户 C：已有用户 | 1-2 人 | 使用已经设置密码的 Active 账号 |
| 用户 D：邀请用户 | 1-2 人 | 可与用户 A 重叠，但必须从邀请链接进入 |

正式邀请 5-10 人之前，先由 1-2 名内部测试者完成三台真实设备烟测。

## 4. 测试前准备

- 为每位测试者分配匿名编号，例如 `BETA-A01`，反馈中不使用真实姓名。
- 准备新的测试手机号、一个已有 Active 账号和至少一个有效邀请码。
- 指定一名平台核验人，只核对测试结果，不在文档中复制数据库密钥或用户隐私。
- 每个场景记录开始时间、结束时间、入口 URL、设备、浏览器和结果。
- 发现 P0 问题时暂停新增邀请，不继续扩大测试人数。

## 5. 用户 A：普通指导师

流程：

手机号验证 → 设置密码 → 选择普通指导师 → 提交申请 → 自动 Active → 进入工作台

用户侧验证：

- 能收到验证码并完成验证；
- 注册页面信息可理解、可输入、可提交；
- 提交后不进入 pending；
- 自动进入工作台；
- 右上角显示指导师身份；
- 显示 500 积分；
- 显示个人邀请码；
- 刷新页面后账号状态、积分和邀请码不丢失。

平台核验：

- 用户和指导师档案均为 Active；
- `credit_wallets` 余额为 500；
- `credit_logs` 存在对应注册奖励流水，余额与钱包一致；
- `invite_codes` 存在该指导师的真实邀请码；
- 不存在重复奖励、重复邀请码或前端本地假余额。

通过标准：上述用户侧和平台侧检查全部一致。

## 6. 用户 B：机构身份

流程：

手机号验证 → 设置密码 → 选择服务中心或分公司 → 提交申请 → pending

用户侧验证：

- 提交后进入待审核页面；
- 不能进入指导师工作台；
- 直接打开工作台 URL 时仍被路由到待审核或登录状态；
- 看不到钱包余额、邀请码和积分流水；
- 页面明确说明等待平台审核，不暗示已经开通。

平台核验：

- 用户、档案和审核申请处于 pending；
- 未发放 500 积分；
- 未生成可用邀请码；
- 未产生普通指导师注册奖励流水。

通过标准：pending 生命周期和权限隔离全部符合现有规则。

## 7. 用户 C：已有用户

流程：

手机号和密码登录 → 直接进入工作台

验证：

- 不被错误送回注册页；
- Active 指导师直接进入工作台；
- 账号身份、钱包余额、积分流水和邀请码与登录前数据一致；
- 退出后再次打开工作台会回到登录页；
- 错误密码只显示友好提示，不显示堆栈、数据库或内部服务细节。

通过标准：既有账号不重复注册，身份和资产数据不变化。

## 8. 用户 D：邀请用户

入口格式：

`https://aipiwen-ai-understanding-99r5kuzk9-guo-yanling-s-projects.vercel.app/login.html?invite=TEST_CODE`

流程：

邀请链接 → 手机号验证 → 注册 → 提交申请 → 确认邀请归属

验证：

- 登录前后的 URL 流程不丢失邀请码；
- 进入注册页后邀请码自动带入；
- 用户不需要手工重复输入已经有效的邀请码；
- 提交申请后，服务端收到同一邀请码；
- 平台核验 `invite_relations` 的邀请人与被邀请人关系正确；
- 无效或篡改邀请码不会建立错误归属。

通过标准：页面、提交参数和最终邀请关系三处一致。

## 10. 反馈回收闭环

1. 测试者完成一个场景后，复制填写 `AIPIWEN_V3_BETA_FEEDBACK_TEMPLATE.md`。
2. 负责人给每条问题分配编号，例如 `BETA-20260725-001`。
3. 按严重度分级：
   - P0：无法登录、权限越权、资产错误、隐私或安全问题；
   - P1：核心流程无法完成，但有明确影响范围；
   - P2：可以完成，但存在明显理解或操作障碍；
   - P3：文案、视觉或低影响体验建议。
4. 状态统一使用：`NEW`、`CONFIRMED`、`FIXING`、`READY_FOR_RETEST`、`CLOSED`、`DEFERRED`。
5. P0 立即暂停新增邀请；P1 在扩大测试前处理；P2/P3 进入 Beta 待办。
6. 关闭问题必须记录修复 Commit、Preview Deployment ID、复测人员和复测证据。

## 11. 首批邀请门槛

邀请 5-10 名测试用户前必须满足：

- 三类真实设备验收均有明确 PASS/FAIL 记录；
- 用户 A-D 至少各完成一次真实流程；
- 没有未关闭 P0；
- Beta 入口仍指向本计划记录的部署；
- 反馈负责人、问题编号和复测机制已经确定。
