## 1. 一句话定义

AIPIWEN.cn 是一个面向个人、家庭和从业者的 AI 理解工具。

它不把人简单归类，也不做诊断，而是把用户观察到的行为、已有测评报告、皮纹/ATD/TRC 等资料，转化成更容易理解的沟通建议、成长线索和关系理解。

核心价值不是“给标签”，而是让用户产生：

> 原来这个行为背后有原因，我可以换一种方式理解和沟通。

---

## 2. 当前产品定位

### 2.1 对 C 端用户

AIPIWEN 是一个帮助用户读懂自己、孩子、伴侣和身边人的 AI 理解入口。

用户不需要先懂皮纹、脑科学或人格模型，只需要输入真实行为、上传已有报告，或做轻量速测，就可以获得更贴近生活场景的解释和建议。

### 2.2 对从业者

AIPIWEN 是一个辅助从业者服务客户的工具。

它不替代咨询师、解读师或教育从业者，而是帮助他们完成前半段信任破冰、行为翻译、报告解读和客户持续沟通。

### 2.3 对服务商 / 机构

AIPIWEN 后续可以作为服务商和机构的客户理解工具。

机构可用它承接家长、学员、客户或团队成员的行为理解、报告解读和持续服务，但目前渠道/服务商能力仍属于本地 Phase 1 演示闭环，不应直接视为线上可用后台。

---

## 3. 产品核心原则

1. 先理解行为，再进入报告。
2. 先降低防备，再建立关联。
3. 报告是理解线索，不是结论。
4. 不诊断，不治疗，不预测未来。
5. 不给孩子、伴侣、客户贴负面标签。
6. 不把皮纹、ATD、TRC 表达成决定命运的工具。
7. 对外统一使用 AIPIWEN / 沐海星辰语言体系，不外露商业机构内部来源表述。

## 4. 当前主要功能模块

## 4.1 AI 行为理解

### 页面入口

- 首页：`homepage.html`
- 行为理解聊天页：`child-chat.html`
- 旧输入页：`behavior-input.html`

### 当前用途

用户输入一个真实行为，例如孩子拖拉、伴侣沉默、客户抗拒、同事沟通困难。

系统尝试将行为翻译成：

- 表面行为
- 可能的底层需求
- 情绪逻辑
- 沟通建议
- 下一步可以怎么说、怎么做

### 当前场景

首页目前存在多类“读懂”入口，主要对应：

- 读懂孩子
- 读懂自己
- 读懂伴侣
- 读懂合作伙伴 / 工作关系

这些入口的长期方向应根据年龄、身份和关系场景，给出不同的问题选项，而不是所有年龄段共用同一批问题。

### 当前技术状态

- `child-chat.html` 使用前端页面承接对话。
- 会使用 `localStorage` 保存部分会话/引导数据。
- 后端主要通过 `/api/guest-chat` 承接 AI 对话。
- 是否有完整长期记忆能力，需按线上 Redis 和当前 API 状态重新核验。

## 4.2 天赋底色 / 皮纹速测

### 页面入口

- `fingerprint-v2-wizard.html`
- 结果页相关：`fingerprint-result.html`，以及轻量报告页 `light-report.html`

### 当前用途

用户通过轻量选择或填写方式，初步了解自己的基础倾向。

产品表达上建议逐步从“皮纹速测”向“天赋底色速测”过渡，以降低普通用户对“皮纹/指纹”技术词的防备。

### 当前边界

该功能只适合作为理解倾向和沟通方式的参考。

不应表达为：

- 精准诊断
- 测出问题
- 判断命运
- 判断疾病
- 判断攻击性
- 决定职业或亲密关系结果

## 4.3 已有报告上传与 AI 报告解读

### 页面入口

- `report-upload.html`

### 当前用途

用户已有 TRC/ATD/皮纹类报告时，可以上传报告图片，让系统辅助识别基础数据，并生成个性化解读内容。

### 当前真实能力

当前上传报告功能更接近“图片识别 + 报告生成”的 MVP，不是完整 OCR/PDF 报告解析系统。

当前已知能力包括：

- 支持图片上传。
- 使用 `FileReader` 和 `canvas` 对图片做前端读取/压缩。
- 调用 `/api/extract-fp` 识别十指 TRC、ATD、姓名、生日/年龄等信息。
- 调用 `/api/generate-report` 生成报告内容。
- 通过 `api/report-store.js` 或相关路由保存/读取报告。

当前不足包括：

- 不应宣称已完整支持 PDF 多页解析。
- 不应宣称已完整 OCR 所有报告正文。
- 年龄应由后台根据生日和当前日期计算为整数年龄，前台只显示结果。
- 可选问题应根据年龄段和使用场景变化，而不是所有年龄段使用同一组问题。
- 报告输出应接入 Report OS 的资料完整度、风险等级、置信度、追问、降级和转人工规则。

## 6. 数据与存储现状

### 6.1 前端本地存储

当前多个页面会使用：

- `localStorage`
- `sessionStorage`

用途包括：

- 用户行为输入
- ref / invite token
- 会话临时数据
- 报告深聊数据
- 速测 uid 或结果信息

上线前要重点检查：

1. 是否保存过多敏感信息。
2. 是否可能在共享设备上泄露。
3. 是否需要过期机制。
4. 是否需要用户主动清除入口。

### 6.2 后端存储

后端主要依赖 Redis 能力，公共封装在 `api/_lib.js`。

涉及：

- 报告存储
- 邀请/归因
- 访客对话
- 可能的租户/服务商数据

生产上线前必须确认 Redis key 命名、隔离策略和清理策略。

## 7. 语言体系与表达边界

## 7.1 对外统一语言

对外输出必须统一为 AIPIWEN / 沐海星辰语言体系。

不应在用户可见内容中出现内部商业机构来源，例如：

- 艾尔发
- 359
- 三家观点

这些会让用户误以为平台在拼接多个外部机构观点，削弱品牌一致性。

## 7.2 可保留的专业背书

来自书籍、论文、教授、公开研究或行业基础知识的表达，可以谨慎保留，但要注意语气。

例如：

- 皮纹与胚胎发育相关
- 遗传度相关研究
- 终生稳定性相关描述

但必须避免把研究结论包装成绝对判断。

## 7.3 禁止表达

前台、报告、AI 输出中应避免：

- 诊断
- 治疗
- 心理疾病判断
- 问题孩子
- 注定
- 一定会
- 精准预测
- 攻击性检测
- 天赋决定命运
- 关系一定适合/不适合
- 职业一定适合/不适合

推荐表达：

- 可能
- 倾向于
- 更容易
- 可以作为理解线索
- 建议进一步结合真实情境判断
- 如果已经影响生活/学习/关系，建议寻求专业支持

## 8. 当前最重要的产品风险

## 8.1 上传报告能力容易被用户误解

如果页面说得太满，用户会以为系统能完整解析所有报告、PDF 和图片。

当前应更克制地表达为：

> 上传已有报告图片，系统先识别关键数据，并生成一份快速读懂报告。

## 8.2 年龄逻辑必须后台统一计算

年龄影响：

- 问题推荐
- 报告内容
- 沟通建议
- 风险边界
- 报告视觉风格

不能让用户自己算，也不能出现小数年龄。

建议统一：

- 后台读取生日
- 使用当前日期计算整数年龄
- 前台只展示：`X 岁`

## 8.3 不同年龄段的问题必须不同

读懂孩子、读懂自己、读懂伴侣、读懂合作伙伴，都不应共用同一套问题。

至少应按以下维度拆：

- 学龄前
- 小学
- 初中
- 高中
- 大学生/青年
- 成人
- 中年

每个年龄段的问题，应对应真实生活压力，而不是泛泛的“关系/成长/职业”。

## 8.4 Report OS 尚未完全接入前台

当前已有 Report OS 文档和 P0 决策 API，但前台是否完整调用，需要单独验收。

不能在市场表达中宣称完整 Report OS 已上线，除非完成端到端测试。

## 9. 当前不建议继续扩张的功能

在上传报告 P0 稳定前，不建议继续扩张：

- 完整长报告
- 亲密关系正式合看
- 亲子关系正式合看
- 合伙人合看
- 团队画像
- 班级画像
- 企业画像
- 支付
- 自动结算
- 自动开票
- CRM
- 自动采集指纹
- 多页 PDF/OCR 解析

当前更重要的是把一个用户上传报告后的“快速读懂”做稳。

## 10. 下一步建议

## 10.1 短期优先级

1. 修正上传报告确认页：
   - 只保留姓名、年龄、ATD 三个展示框。
   - 年龄后台计算，前台只显示整数。
   - ATD 显示明确为“ATD 角度”或“ATD”。

2. 重做问题推荐逻辑：
   - 根据年龄段给不同问题。
   - 根据使用场景给不同问题。
   - 每次最多推荐 3 个核心问题，避免生成压力过大。

3. 接入 Report OS P0：
   - 资料完整度
   - 风险等级
   - 置信度
   - 信息不足追问
   - 安全降级
   - 转人工提示

4. 统一语言体系：
   - 清理商业机构名外露。
   - 保留合理学术/行业背书。
   - 所有输出转为 AIPIWEN / 沐海星辰表达。

## 10.2 上线前必须验收

1. 首页入口文案是否统一。
2. 行为理解四类场景的问题是否按年龄变化。
3. 上传报告是否只展示后台计算好的年龄。
4. 上传报告是否不再出现小数年龄。
5. 报告生成失败时是否有可理解的提示。
6. R2/R3 风险是否能安全降级。
7. API 是否没有打印用户隐私和密钥。
8. `vercel.json` 是否没有混入未确认路由。
9. 线上 Redis key 是否可控。
10. 未成年人相关表达是否足够克制。

## 11. 给后续开发者的执行规则

1. 不要在没确认分支和工作区状态前开发。
2. 不要把渠道/服务商分支改动混入上传报告任务。
3. 不要把 docs-only 分支当成生产状态。
4. 不要为了视觉统一重构整站。
5. 页面已经可用时，优先做最小差异修补。
6. 任何涉及上线、Vercel、Redis、环境变量的操作必须单独确认。
7. 任何涉及 OpenAI/Claude API key 的任务，不得打印、提交或写入真实密钥。
8. 报告系统先做 P0 快速读懂，不直接扩张到完整报告宇宙。

## 12. 当前交底结论

AIPIWEN.cn 当前已经具备三个核心方向：

1. 行为理解入口。
2. 天赋底色 / 皮纹速测入口。
3. 已有报告上传与 AI 解读入口。

但当前最关键的产品建设点不是继续扩张功能，而是把“上传已有报告后，用户能稳定得到一份可信、克制、贴近自己的快速读懂报告”做扎实。

下一阶段应围绕 Report OS P0，把资料完整度、风险等级、置信度、追问、降级、转人工这些底层规则接进真实用户路径。
