# AIPIWEN Report OS V0.9 总体验收与产品改造准备清单

## 1. 结论

Report OS V0.1-V0.8 已形成从资料吸收、方法论提炼、指标本体、报告模板、Schema、Prompt Pack、测试样本、安全拦截到产品改造准备的基本闭环。

明确结论：

- Report OS 已具备上传报告 P0 改造前置条件。
- 但不适合一次性开放全部报告类型。
- 下一轮代码只做最小 P0。
- 关系合看、团队、班级、企业、长期陪伴先内测。

## 5. 不能直接进入前台的内容

| 内容 | 为什么不能前台 | 可否内部参考 | 安全改写方向 |
| --- | --- | --- | --- |
| 医学/心理相关 | 涉及诊断、治疗和专业资质风险 | 可以 | 建议专业评估，报告只作理解参考 |
| 脑科学强结论 | 容易夸大科学性，把研究方向说成确定事实 | 可以 | 改为远期研究或观察方向 |
| 医养/康养 | 涉及医疗健康承诺 | 可以 | 不作为当前产品能力 |
| 全生命周期宏大叙事 | 容易变成大而全承诺 | 可以 | 改为分龄理解与陪伴 |
| 玄学化表达 | 容易被理解为算命、命理、神秘化 | 不建议 | 改为行为模式和沟通节奏 |
| 命定化表达 | 会忽略环境、训练和现实选择 | 不建议 | 改为倾向、场景和验证 |
| 对孩子标签化 | 对未成年人有伤害性和歧视风险 | 不建议 | 改为行为不等于标签 |
| 对关系下结论 | 可能干预重大关系选择 | 可以作为风险样本 | 改为差异翻译和沟通动作 |
| 对职业/升学保证 | 涉及重大决策和结果承诺 | 可以作为反向样本 | 改为探索方向和小步验证 |
| 对企业/学校人员筛选 | 涉及歧视、隐私和数据滥用 | 可以作为边界样本 | 改为群体支持和协作机制 |

## 6. 上传报告产品改造最小范围 P0

下一轮真正动代码时，只建议做 P0：

1. 上传报告后先解析资料，不生成结论。
2. 识别用户身份、报告对象和用户目的。
3. 识别风险等级 R0-R3。
4. 判断置信度 high / medium / low / insufficient。
5. 低风险 R0/R1 且 high/medium 时，只生成快速读懂报告。
6. 中风险、字段缺失或用户目的不清时，先追问。
7. 高风险 R2 进入降级输出。
8. R3 阻断普通报告，提示人工专家或专业支持。

### 6.1 先不做的功能

- 个人完整长报告自动生成。
- 亲子、亲密、合伙人、团队正式报告生成。
- 班级画像和企业团队画像。
- 长期陪伴和阶段复盘。
- 官网表达升级。
- 自动知识卡沉淀。
- 任何 deploy 或线上发布。

### 6.2 先只做内部测试的场景

- 关系合看。
- 团队协作。
- 班级/学校场景。
- 企业场景。
- 职业重大转型。
- 孩子高敏感行为。
- 用户说“报告不准 / 不像我”。

### 6.3 必须拦截的风险

- 医学和心理诊断。
- 自伤、暴力、严重危机表达。
- 升学保证和成绩预测。
- 职业命定和重大职业决策。
- 关系去留、分手、结婚、离婚判断。
- 招聘淘汰、员工筛选、风险学生标签。
- 未授权他人资料或未成年人资料。

## 8. 推荐执行顺序 A-G

推荐顺序：

1. A. 先回退 `homepage.html`。
2. B. 生成 Report OS 总体验收报告。
3. C. commit docs。
4. D. 新建上传报告产品改造任务或分支。
5. E. 改前端/API。
6. F. 本地测试。
7. G. 再考虑 deploy。

理由：

- A 先清掉失败首页改版遗留，避免污染后续提交。
- B 固化产品改造依据，防止下一轮代码偏离 Report OS 边界。
- C 先提交 docs，保住 V0.1-V0.8 的知识资产。
- D 在干净基础上进入产品改造，便于回滚和审查。
- E 只做 P0，避免一次性开放复杂报告。
- F 用 V0.7 正向、反向、R0-R3 和降级样本做本地验证。
- G 只有本地验证通过后，才考虑 deploy。

## 9. 下一轮代码改造边界

下一轮如果动代码，必须遵守：

- 只做上传报告 P0。
- 不改 Report OS 文档内容，除非另开 docs 任务。
- 不开放关系合看、团队、班级、企业和长期陪伴给前台用户。
- 不让 R2/R3 进入普通报告生成。
- 不让低置信度资料生成完整报告。
- 不用报告做医学、心理、升学、职业、关系、招聘、学校筛选结论。
- 不把行业大会或外部机构原话直接作为前台文案。
