## 2. 当前 mock API 定位

`lib/report-upload-p0-dryrun.js` 当前只是：

- JSON-only。
- mock/rules。
- 本地规则分流样机。
- 非部署 dry-run 模块，不是生产 API route。
- 不处理真实文件上传。
- 不调用 AI。
- 不写数据库。
- 不读 Obsidian。
- 不代表生产服务。

它的作用是验证 Report OS V1.0 P0 的基本分流逻辑：用户上传或粘贴材料后，系统先判断风险、置信度和输出路径，再决定快速读懂、追问、降级或转人工。

当前 mock API 不能直接作为生产接口使用。后续进入真实 P0 API 时，再决定是否合并到现有 API 或调整部署方案。

## 3. 当前 mock API 已验证能力

当前 mock API 已验证：

- R0 / R1 / R2 / R3 风险等级。
- `high / medium / low / insufficient` 置信度。
- 输出路径决策表。
- 未成年人风险提升。
- 诊断 / 医学 / 心理风险拦截。
- 关系 / 团队 / 学校 / 企业场景降级或阻断。
- debug 默认关闭。
- debug 开启时不返回 `reportText` 原文全文，只返回 `reportTextLength` 等摘要信息。
- 8 个 JSON 样本验证通过。

8 个样本覆盖：

1. 普通本人快速读懂。
2. 家长理解孩子行为。
3. 未成年人 + 诊断倾向。
4. 关系去留判断。
5. 企业招聘筛选。
6. 信息不足。
7. 职业 / 升学保证。
8. debugMode 开关。

## 4. 真实 P0 不能直接上线的原因

当前 mock API 不能直接上线，原因包括：

- 无鉴权。
- CORS 仍是 mock 默认。
- 无速率限制。
- 无真实上传解析。
- 无文件大小限制。
- 无文件类型限制。
- 无日志脱敏机制。
- 无人工复核后台。
- 无真实 Prompt 调用链。
- 无完整样本测试矩阵。
- 无生产级 Schema 校验。
- 无异常审计和回滚策略。
- 无未成年人、他人报告、学校/企业场景的完整授权链路。

因此下一步不能直接把当前 mock API 接到前台生产入口，而应先做工程分层和灰度前置工作。

## 5. 真实 P0 工程模块拆分

真实 P0 建议拆成 10 层。

| 层级 | 名称 | 职责 |
| --- | --- | --- |
| 1 | Upload Intake 层 | 接收上传入口，包括图片、文本、后续 PDF 或结构化数据；负责请求大小、类型和基础格式限制 |
| 2 | File/Text Parse 层 | 从上传内容中提取可读文本、结构化字段和报告片段；不做结论生成 |
| 3 | Consent & Identity 层 | 识别用户身份、报告对象、年龄、关系、授权状态和用途边界 |
| 4 | Risk Assessment 层 | 按 R0-R3 判断医学、心理、未成年人、关系、学校、企业、筛选、升学和职业风险 |
| 5 | Confidence Assessment 层 | 按资料完整度、字段充足度、目的明确度、授权和风险等级判断置信度 |
| 6 | Output Decision 层 | 决定 quick reading、追问、降级、转人工或专业支持 |
| 7 | Prompt Orchestration 层 | 在允许生成时按 Prompt Pack 路由调用，不允许一个大 Prompt 直接生成 |
| 8 | Safety Rewrite 层 | 对草稿进行安全改写，去除诊断、绝对化、标签化、玄学化和筛选表达 |
| 9 | Human Review Trigger 层 | 对 R2/R3、复杂个案、机构客户、未成年人高风险和重大决策触发人工复核 |
| 10 | Audit Log 层 | 记录脱敏后的 upload_id、风险等级、置信度、输出路径、降级原因和人工复核原因 |

工程原则：

- 解析层不生成结论。
- 风险判断必须在生成前。
- 置信度必须在生成前。
- R3 不进入普通 Prompt。
- R2 只进入降级或人工复核路径。
- 审计日志不得存储原始敏感全文。

## 6. 前端上传入口对接原则

前端上传入口必须保持克制：

- 前端不直接承诺完整报告。
- 上传前必须显示授权 / 隐私提醒。
- 涉及他人、孩子、学生、团队或企业资料时，必须提示用途边界。
- 上传后先显示“正在解析与安全判断”，不能直接显示“正在生成完整报告”。
- 输出结果必须是以下之一：快速读懂、追问、降级、转人工。
- 不展示内部 debug。
- 不展示风险命中词。
- 不展示“心理诊断式”提示。
- 不展示医学、疾病、脑科学强判断。
- 不把 R0-R3、confidence 等内部字段直接裸露给普通用户。

前端文案只能表达：

- 当前资料支持做什么。
- 当前资料不支持做什么。
- 为什么需要补充问题。
- 为什么建议人工或专业支持。

## 7. 后端 API 演进路线

从当前 `lib/report-upload-p0-dryrun.js` 演进建议如下：

| 阶段 | 名称 | 目标 | 禁止越界 |
| --- | --- | --- | --- |
| P0.1 | JSON mock rules | 保持当前 JSON-only 规则分流，验证 R0-R3、置信度、输出路径 | 不接 AI、不接上传、不写库 |
| P0.2 | 文本输入真实解析 | 对用户粘贴文本做字段提取、意图识别和风险判断 | 不处理真实文件，不生成完整报告 |
| P0.3 | 文件上传但仅解析文本 | 接入文件上传入口，只提取文本或结构化摘要 | 不做多页复杂 OCR 承诺，不长期存原文 |
| P0.4 | 接 Prompt Pack 生成快速读懂 | 只在 R0/R1 + high/medium 下调用快速读懂 Prompt | 不开放完整长报告和关系/团队报告 |
| P0.5 | 人工复核队列 | 对 R2/R3、机构、未成年人、高风险场景建立复核入口 | 不自动交付高风险结果 |
| P0.6 | 灰度上线 | 小范围放量，监控样本、风险、转人工、失败路径 | 不全量开放，不接 Obsidian 生产链路 |

每个阶段都必须有独立验收，不能把后续阶段能力提前混入 P0.1/P0.2。

## 8. Prompt 调用链原则

后续真实 Prompt 调用必须沿用 Report OS V1.0 拆分链路：

1. 报告解析 Prompt。
2. 用户身份与目的识别 Prompt。
3. 风险判断 Prompt。
4. 置信度判断 Prompt。
5. 输出路径选择 Prompt。
6. 快速读懂报告 Prompt。
7. 追问生成 Prompt。
8. 降级输出 Prompt。
9. 转人工建议 Prompt。
10. 安全改写 Prompt。

硬规则：

- 风险判断必须发生在报告生成前。
- 置信度判断必须发生在报告生成前。
- R3 不调用普通报告 Prompt。
- R2 不调用完整报告 Prompt。
- low / insufficient 不生成完整报告。
- Prompt 输出必须再经过安全改写。
- Prompt 失败时进入追问、降级或转人工，不能强行生成。

## 9. Schema 对接原则

真实 Schema 目录必须使用：

```text
docs/aipiwen_report_system/08_schema_结构化规则/
```

至少需要对接以下 Schema：

| Schema | 用途 |
| --- | --- |
| `ReportUploadInputSchema` | 接收上传输入、用户身份、目的和基础上下文 |
| `ReportParseResultSchema` | 表示解析结果、可读性、已识别字段和缺失字段 |
| `UserIdentitySchema` | 标准化本人、父母、老师、顾问、伴侣、合伙人、企业/学校人员等身份 |
| `UserIntentSchema` | 标准化快速读懂、孩子行为、学习/职业、关系、团队、学校、医学心理、未知目的 |
| `SensitiveScenarioSchema` | 标记未成年人、医学心理、自伤暴力、关系、学校、企业、隐私授权等敏感场景 |
| `RiskAssessmentSchema` | 输出 R0-R3、risk flags、风险原因和系统动作 |
| `ConfidenceAssessmentSchema` | 输出 high/medium/low/insufficient、缺失字段和允许输出深度 |
| `OutputDecisionSchema` | 决定 quick reading、追问、降级、转人工或专业支持 |
| `QuickReadingReportSchema` | 限定快速读懂报告的 7 个 P0 章节 |
| `ClarificationQuestionSchema` | 限定追问数量、追问原因和用户不回答时的降级路径 |
| `FallbackOutputSchema` | 限定降级输出结构和禁止输出范围 |
| `HumanReviewTriggerSchema` | 标准化人工复核触发原因、风险等级和资料摘要 |

代码阶段不能引用不存在的 `08_schema_结构化输出/` 路径。

## 10. 测试验收扩展

当前 8 个样本只证明 mock/rules 基本分流可用。下一阶段至少扩展到：

- 20 个正向样本。
- 25 个高风险负向样本。
- R0-R3 风险矩阵。
- 未成年人样本。
- 关系样本。
- 企业 / 学校禁用样本。
- debug 安全样本。
- 文件上传异常样本。
- 授权缺失样本。
- 低置信度资料样本。
- Prompt 失败降级样本。

每个测试样本必须记录：

- 输入。
- 期望风险等级。
- 期望置信度。
- 期望输出路径。
- 是否应追问。
- 是否应降级。
- 是否应转人工。
- 禁止输出内容。
- 实际输出。
- 是否通过。

上线前最低要求：

- 高风险反向样本拦截通过率 100%。
- R3 不得进入普通报告生成。
- 未成年人、关系、学校、企业样本必须人工验收。
- debug 默认关闭，并且不返回敏感原文全文。

## 11. Obsidian 与专家课程暂不接入生产 P0

Obsidian 是长期知识矿山，不是 P0 生产接口的数据源。

专家课程、外部课程、书籍和案例后续可以进入 Obsidian 原始知识库，但不能原文进入前台报告生成层。

进入 Report OS 或前台生成前，必须完成：

1. 知识卡提取。
2. 内容分级。
3. 安全改写。
4. 人工审核。
5. 测试样本验证。
6. 禁用内容隔离。

P0 上传报告功能不直接读 Obsidian，不自动沉淀知识卡，不把心理、催眠、疗愈、原生家庭、症状转化、潜意识、儿童人格等内容原文用于前台生成。

## 12. 下一步执行建议

建议顺序：

1. 提交本工程对接设计说明。
2. 再进入 P0.2 文本输入真实解析。
3. 再做 Prompt Pack 调用 dry-run。
4. 再接文件上传。
5. 再做人工复核。
6. 最后灰度上线。

进入 P0.2 前，应先确认：

- 当前工作区干净。
- API mock 已提交。
- V1.0 规则冻结包已提交。
- Schema / Prompt / Test Case 路径明确。
- 不涉及首页、页面设计、商业包装或部署。

## 13. 禁止事项

真实 P0 前仍禁止：

- 直接开放完整长报告。
- 关系正式合看。
- 团队 / 班级 / 企业画像。
- 招聘筛选。
- 学生分层。
- 医学 / 心理判断。
- 脑科学强结论。
- 催眠 / 疗愈建议。
- 职业 / 升学保证。
- Obsidian 直接生产接入。
- 自动知识卡沉淀。
- 未授权使用他人、未成年人、学校、企业资料。
- 把 debug、风险命中词或内部判断裸露给前台用户。

本设计说明的结论：真实 Report Upload P0 的第一目标不是扩大生成能力，而是把“上传后先判断、再决定输出路径”的安全链路工程化。
